# crs

The coordinate pipeline, and the realm rule Decision 3 puts on one part of it.

`resolveCrsDefinition(wkt)` cuts the horizontal system (`PROJCS`, or `GEOGCS` when there is none) out of the file's WKT and answers with that node, or throws saying why it cannot be trusted. A compound WKT makes proj4 throw, so the vertical half never reaches it. And a WKT that states no datum shift gets none from proj4, which is right only for a datum EPSG publishes a zero shift to WGS 84 for — the table in `null-shift-datums.ts`, with the query that generated it and the measurement behind it. Any other datum is refused with `CrsDefinitionRequiredError`, as is a WKT proj4 cannot read; a WKT that names no EPSG code at all gets `CrsCodeNotFoundError`. A file with no WKT never reaches the resolver: `fromUrl` refuses it with `WktNotInVlrsError`. Each tells the caller to pass `fromUrl(url, { crs })`, which replaces the file's description and skips this step. `createTransformFromDefinition(definition)` turns either answer into a `CrsTransform`, whose two members project file coordinates to WGS84 degrees and metres (`toWgs84`, which the tileset's regions are built from) and to ECEF metres (`toEcef`).

The rule is about the resolver, not about the builder. The resolver's refusals have to reject `fromUrl`, and thrown inside a Worker they would reach the caller as an opaque `messageerror`. So the resolver stays on the main thread, and what crosses to a Worker is the resolved definition string; the transform itself is a closure and could not cross in any case. `createTransformFromDefinition` is realm-free: the main thread builds one at `fromUrl` time, for the synthetic tileset's regions and its root geometric error. `worker.ts` exists to make the separation checkable rather than to say where the builder runs — `tests/crs-worker-boundary.test.ts` walks everything that entry can reach, statically or dynamically, and fails if the resolver is among it.

Three v1 limits. Height is ellipsoidal by default — a caller-supplied `geoidHeight` constant corrects it, per §6. z is taken to be in the same linear unit as x and y, because proj4 scales only the horizontal pair and the definition is where that unit is read from; a file measuring height in some other unit comes out vertically scaled. And a definition has to stand on its own: one naming `+nadgrids` for anything but the self-contained `@null` sentinel depends on realm-global state loaded separately, one written as a `proj4.defs` alias rather than a `+proj=` parameter string depends on realm-global state registered separately, and one that is a `+`-parameter string but never names a projection at all cannot build one regardless of realm — on proj4 2.21, left unguarded, these show up as `[NaN, NaN]` coordinates or a thrown non-Error. `createTransformFromDefinition` refuses all three up front with `CrsDefinitionUnusableError` instead.
