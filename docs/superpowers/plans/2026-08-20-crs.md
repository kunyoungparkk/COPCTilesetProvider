# CRS Registry and Transform Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn a file's WKT into a coordinate transform, by extracting only the horizontal EPSG code, resolving it against a registry the caller populates, and projecting through WGS84 into ECEF.

**Architecture:** Three small units and a composition. A bracket-aware scanner finds the horizontal CRS node and reads its own authority code; a `Map` holds proj4 definitions with EPSG:4326 registered by default; a closed-form function turns geodetic degrees into ECEF metres. `createTransform` composes them.

**Tech Stack:** TypeScript 7 (browser ESM), Vitest, `proj4` (already an approved dependency).

**Spec:** `OVERVIEW.md` — §3 Decision 6 (the CRS rules and the error contract), §6 (heights are ellipsoidal; geoid correction is out of scope for v1).

## Global Constraints

- Node 22 for all commands. This machine's default `node` is v18, so every command below assumes `export PATH=/home/kyp/.local/node22/bin:$PATH` first.
- No new runtime dependencies. OVERVIEW §5 fixes the set at `copc`, `laz-perf`, `proj4`; `tests/manifest.test.ts` fails the build if that changes.
- **Never hand whole WKT to proj4.** Decision 6 forbids it outright: compound systems and dialects go quietly wrong. This module extracts a code and looks it up; it never passes WKT text to the projection library.
- **Only EPSG:4326 is registered by default.** Decision 6 chose one rule — "if it isn't 4326, register it" — over a partial built-in table, because there is no predicting which systems arrive.
- Error messages are public API (Decision 6), and this module's errors carry a specific obligation: **the code extracted from the file, and a copy-pasteable `registerCrs` call with that code already in it.**
- Comments explain *why*, and cite the OVERVIEW decision or section that forced the choice.
- Tests never touch the network. They read pinned bytes from `fixtures/`.
- Commits: `type(scope): summary`, imperative, **under 72 characters**, with a body explaining why. No `Co-Authored-By` or `Signed-off-by` trailers.

## What the anchor fixture proved, and why a regex will not do

Autzen's WKT — already pinned in `fixtures/autzen-vlrs.bin` — is a compound system with **ten** `AUTHORITY` nodes:

```
COMPD_CS[
  PROJCS[ …
    GEOGCS[ … AUTHORITY["EPSG","4269"] ]     ← nested, depth 3
    … AUTHORITY["EPSG","2992"] ]             ← the horizontal code, depth 2
  VERT_CS[ … AUTHORITY["EPSG","6360"] ]      ← the vertical datum, depth 2
]
```

Measured, not assumed. The full list, with the keyword each one sits directly inside:

| code | inside | depth |
|---|---|---|
| 7019 | `SPHEROID` | 5 |
| 6269 | `DATUM` | 4 |
| 8901 | `PRIMEM` | 4 |
| 9122 | `UNIT` | 4 |
| **4269** | `GEOGCS` | 3 |
| 9002 | `UNIT` | 3 |
| **2992** | `PROJCS` | 2 |
| 5103 | `VERT_DATUM` | 3 |
| 9003 | `UNIT` | 3 |
| **6360** | `VERT_CS` | 2 |

Three naive strategies and what each returns here:

- **last `AUTHORITY`** → 6360, the *vertical* datum. Silently the wrong CRS.
- **first `AUTHORITY`** → 7019, a *spheroid*. Not a CRS at all.
- **any `AUTHORITY` directly inside `PROJCS` or `GEOGCS`** → matches both 2992 and 4269, because the geographic CRS is nested inside the projected one.

The rule that works: **the authority node that is a direct child of the horizontal CRS — `PROJCS` when there is one, otherwise `GEOGCS`.** "Direct child" cannot be decided by a regular expression over nested brackets, so this task writes a small scanner.

§6 puts geoid correction out of scope and treats heights as ellipsoidal, so v1 transforms horizontally and passes height through. The vertical code is deliberately not read.

## How the transform is verified, and what that does not cover

Decision 6 says the accuracy test compares the pipeline against **PDAL ground truth**. PDAL is not installed on this machine and cannot be — there is no `pip` and `apt` needs privileges we do not have. Rather than substitute a different authority and quietly change the spec's standard, this plan verifies what it honestly can and records the gap.

What is verified with no external authority:

- **Code extraction** — 2992 is found and 6360 is not, against the real file's bytes.
- **The registry and every error path** — including that the message carries a runnable `registerCrs` call.
- **Geodetic to ECEF** — closed form on the WGS84 ellipsoid, so exact values are known independently: (0°, 0°, 0) is (6378137, 0, 0), (0°, 90°, 0) is (0, 6378137, 0), and the north pole is (0, 0, 6356752.314245).
- **The assembled pipeline, against the Earth.** Running Autzen's own header bounds through it must land on Autzen Stadium. Measured with the definition read off the file's own `PROJCS` parameters:

  | | longitude | latitude |
  |---|---|---|
  | header min | -123.07499 | 44.04972 |
  | centre | -123.06875 | 44.05625 |
  | header max | -123.06251 | 44.06278 |

  The centre lands **0.22 km** from Autzen Stadium's published location (44.0582 °N, 123.0681 °W) — the right distance for a cloud roughly 1 km by 1.4 km that covers more than the stadium itself.

This catches every failure mode this module can actually have, because **this module does not implement a projection**: it extracts a code, looks up a definition, calls proj4, and converts to ECEF. Its plausible bugs are gross — swapped axes, feet read as metres, the wrong definition, the wrong ellipsoid — and each of those moves the result by kilometres or more.

What it does **not** cover: sub-metre accuracy, and specifically the NAD83-to-WGS84 datum difference of one to two metres. That is a property of the *registered definition*, which Decision 6 makes the registrant's responsibility, not the library's. The PDAL comparison stays on the roadmap; do not claim it has been done.

```ts
// src/crs/horizontal-code.ts

/**
 * The keywords that introduce a horizontal coordinate system, best first.
 *
 * A projected system wins over a geographic one because a file that has both
 * has its coordinates in the projected one — and the geographic system is
 * nested inside it, describing the datum it was projected from.
 */
const HORIZONTAL = ['PROJCS', 'GEOGCS'] as const;

/**
 * Finds the EPSG code of the file's horizontal coordinate system.
 *
 * Decision 6 extracts a code and resolves it against a registry rather than
 * handing whole WKT to proj4, because compound systems and dialects go quietly
 * wrong that way. The pinned Autzen file shows how quietly: it carries ten
 * AUTHORITY nodes, and the horizontal one is neither the first (a spheroid)
 * nor the last (a vertical datum).
 *
 * The rule is therefore structural — the authority that is a *direct child* of
 * the horizontal system — which needs bracket depth, not pattern matching.
 * §6 keeps heights ellipsoidal, so the vertical system is never consulted.
 *
 * Returns `null` when there is no such code; the caller decides what that means.
 */
export function findHorizontalEpsgCode(wkt: string): number | null {
  // Keyed by the keyword each authority sits directly inside, so the horizontal
  // system's own code is distinguishable from the ones its parts carry.
  const found = new Map<string, number>();
  const open: { keyword: string; body: number }[] = [];
  let quoted = false;

  for (let i = 0; i < wkt.length; i++) {
    const character = wkt[i];

    // A name may contain anything, brackets included, so quoted spans are
    // skipped rather than scanned.
    if (character === '"') {
      quoted = !quoted;
      continue;
    }
    if (quoted) {
      continue;
    }

    if (character === '[') {
      open.push({ keyword: keywordBefore(wkt, i), body: i + 1 });
      continue;
    }
    if (character !== ']') {
      continue;
    }

    const node = open.pop();
    if (node === undefined || node.keyword !== 'AUTHORITY') {
      continue;
    }

    // The first authority a keyword carries is its own; later ones belong to
    // repeated parts, such as a second UNIT.
    const parent = open[open.length - 1];
    if (parent === undefined || found.has(parent.keyword)) {
      continue;
    }

    const code = epsgCode(wkt.slice(node.body, i));
    if (code !== null) {
      found.set(parent.keyword, code);
    }
  }

  for (const keyword of HORIZONTAL) {
    const code = found.get(keyword);
    if (code !== undefined) {
      return code;
    }
  }
  return null;
}

/** The bare keyword immediately preceding a bracket, e.g. `AUTHORITY` in `AUTHORITY[`. */
function keywordBefore(wkt: string, bracket: number): string {
  let start = bracket;
  while (start > 0 && /[A-Z_]/.test(wkt[start - 1] ?? '')) {
    start--;
  }
  return wkt.slice(start, bracket);
}

const EPSG_BODY = /^\s*"?EPSG"?\s*,\s*"?(\d+)"?\s*$/;

/** Reads `"EPSG","2992"` out of an authority node's body, or `null` if it is not EPSG. */
function epsgCode(body: string): number | null {
  const match = EPSG_BODY.exec(body);
  const digits = match?.[1];
  return digits === undefined ? null : Number(digits);
}
```

> Quoted spans are skipped because a system's name is free text — Autzen's is
> `"NAD83 / Oregon GIC Lambert (ft) + NAVD88 height (ftUS)"`. Nothing in the
> fixture puts a bracket inside a name, but a scanner that would miscount if one
> did is a scanner that fails on the first file that does.

// src/errors/crs.ts
import { CopcTilesetError } from './base.js';

/**
 * The file names a coordinate system nobody registered.
 *
 * Decision 6 registers only EPSG:4326 by default, because there is no
 * predicting which systems arrive and a partial built-in table would be worse
 * than one clear rule. The message therefore has to do the work: it carries the
 * code the file asked for, already inside the call that fixes it.
 */
export class CrsNotRegisteredError extends CopcTilesetError {
  readonly code = 'crs-not-registered';
  readonly epsgCode: number;

  constructor(epsgCode: number) {
    super(
      `This file uses EPSG:${epsgCode}, which is not registered. Only EPSG:4326 is ` +
        'known by default, so every other system has to be supplied once, before the ' +
        'file is opened:\n\n' +
        `    registerCrs(${epsgCode}, '<proj4 definition>');\n\n` +
        `The definition for EPSG:${epsgCode} is at https://epsg.io/${epsgCode} — take ` +
        'its proj4 string. Its accuracy is yours to vouch for; this library only ' +
        'applies what it is given.',
    );
    this.epsgCode = epsgCode;
  }
}

/**
 * No horizontal EPSG code could be read from the file's WKT.
 *
 * Unlike an unregistered code, there is nothing for the caller to register —
 * the file did not say which system its coordinates are in, so the file is what
 * has to change.
 */
export class CrsCodeNotFoundError extends CopcTilesetError {
  readonly code = 'crs-code-not-found';

  constructor() {
    super(
      'No horizontal EPSG code could be read from this file\'s coordinate system ' +
        'description. Its WKT either names no authority or names one this library does ' +
        'not recognise, so there is nothing to look up. Re-writing the file with a ' +
        'current PDAL — `pdal translate input.laz output.copc.laz --writers.copc.a_srs=EPSG:<code>` ' +
        '— will record a system that can be read.',
    );
  }
}

- [ ] **Step 4: Write the registry**

```ts
// src/crs/registry.ts

/**
 * The proj4 definition of every coordinate system this process can transform.
 *
 * Decision 6 seeds it with EPSG:4326 alone. A partial built-in table would
 * invite the question of why one system is present and another absent; one
 * rule — "if it is not 4326, register it" — has no such edge.
 */
const definitions = new Map<number, string>([[4326, '+proj=longlat +datum=WGS84 +no_defs']]);

/**
 * Teaches this process one coordinate system.
 *
 * The definition's accuracy is the caller's to vouch for; Decision 6 is
 * explicit that this library applies what it is given rather than judging it.
 * Registering a code twice replaces the earlier definition, so a caller can
 * correct one without restarting.
 */
export function registerCrs(code: number, definition: string): void {
  definitions.set(code, definition);
}

/** The registered definition for a code, or `undefined` if nobody supplied one. */
export function definitionFor(code: number): string | undefined {
  return definitions.get(code);
}
```

**Interfaces:**
- Consumes: nothing.

> **Why this is exactly testable:** the conversion is closed form on the WGS84 ellipsoid, so reference values are known independently of any library. (0°, 0°, 0) is the intersection of the equator and the prime meridian, at the semi-major axis exactly. That makes this the one part of the pipeline whose correctness needs no external authority at all.
>
> §6 treats heights as ellipsoidal, so `height` goes in as given. A file whose heights are orthometric will sit at a vertical offset, which the README records as a known v1 limitation.

// WGS84. The flattening is the defining constant; the semi-minor axis and the
// first eccentricity follow from it, so they are derived rather than pasted.
const SEMI_MAJOR = 6_378_137;
const FLATTENING = 1 / 298.257_223_563;
const ECCENTRICITY_SQUARED = FLATTENING * (2 - FLATTENING);

const toRadians = (degrees: number): number => (degrees * Math.PI) / 180;

/**
 * Converts geodetic coordinates to Earth-centred, Earth-fixed metres.
 *
 * §6 treats every height as ellipsoidal: geoid correction is out of scope for
 * v1, so a file storing orthometric heights sits at a vertical offset. The
 * README carries that limitation.
 */
export function geodeticToEcef(
  longitude: number,
  latitude: number,
  height: number,
): [number, number, number] {
  const lon = toRadians(longitude);
  const lat = toRadians(latitude);
  const sinLat = Math.sin(lat);
  const cosLat = Math.cos(lat);

  // Radius of curvature in the prime vertical: how far the surface normal
  // travels before it meets the spin axis, which is what height is measured
  // along — not along a ray from the centre.
  const n = SEMI_MAJOR / Math.sqrt(1 - ECCENTRICITY_SQUARED * sinLat * sinLat);

  return [
    (n + height) * cosLat * Math.cos(lon),
    (n + height) * cosLat * Math.sin(lon),
    (n * (1 - ECCENTRICITY_SQUARED) + height) * sinLat,
  ];
}
```

// src/crs/transform.ts
import proj4 from 'proj4';
import { CrsCodeNotFoundError, CrsNotRegisteredError } from '../errors/index.js';
import { geodeticToEcef } from './ecef.js';
import { findHorizontalEpsgCode } from './horizontal-code.js';
import { definitionFor } from './registry.js';

const WGS84 = '+proj=longlat +datum=WGS84 +no_defs';

export interface CrsTransform {
  /** File coordinates to ECEF metres. */
  toEcef(x: number, y: number, z: number): [number, number, number];
}

/**
 * Builds the transform from a file's coordinates to ECEF.
 *
 * Decision 6 fixes this order: read the horizontal code out of the WKT, resolve
 * it against the registry, and hand proj4 a *definition* — never the WKT
 * itself, which goes quietly wrong on compound systems. §6 keeps heights
 * ellipsoidal, so z passes through the projection untouched.
 */
export function createTransform(wkt: string | undefined): CrsTransform {
  const code = wkt === undefined ? null : findHorizontalEpsgCode(wkt);
  if (code === null) {
    throw new CrsCodeNotFoundError();
  }

  const definition = definitionFor(code);
  if (definition === undefined) {
    throw new CrsNotRegisteredError(code);
  }

  const toWgs84 = proj4(definition, WGS84);

  return {
    toEcef(x, y, z) {
      const [longitude, latitude] = toWgs84.forward([x, y]);
      return geodeticToEcef(longitude, latitude, z);
    },
  };
}
```
