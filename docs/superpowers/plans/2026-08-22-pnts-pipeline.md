# PNTS Encoding Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn one COPC node's compressed bytes into the PNTS tile Cesium renders, in one pass that never lets the decoded point array cross a boundary.

**Architecture:** A short pipeline of pure functions — decode, transform, encode — plus two guards that belong at seams this sub-project owns. `copc.js` supplies the LAZ decode and the scale/offset arithmetic; `src/crs` supplies the projection; this module owns RTC_CENTER, the float32 relatives, and the PNTS bytes.

**Tech Stack:** TypeScript 7 (browser ESM), Vitest, `copc` (`Las.PointData.decompressChunk`, `Las.View`), `laz-perf` (reached only through copc.js), `proj4` via `src/crs`.

**Spec:** `docs/superpowers/specs/2026-08-22-pnts-pipeline-design.md`

## Global Constraints

- **Node 22 is required.** The default `node` is v18 and Vitest dies at startup. Prefix every command with `export PATH=/home/kyp/.local/node22/bin:$PATH`.
- **No new dependencies.** OVERVIEW §5 fixes the list at `copc.js`, `laz-perf`, `proj4`; `tests/manifest.test.ts` pins it. `laz-perf` is already a dependency and is reached only through `copc.js`.
- **Tests never touch the network.** Fixtures under `fixtures/` only, committed bytes, regenerated by hand with `scripts/cut-fixtures.mjs`.
- **English** for code, comments, commit messages. Commits `type(scope): summary`, imperative, under 72 chars, body explains *why* and cites the OVERVIEW decision.
- **`tsc --noEmit` clean** under `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `erasableSyntaxOnly`. Imports carry `.js`.
- **The two rules in CLAUDE.md's Open-source standard bind every task here:** write what a test catches only after running the mutation that decides it; comments state what is true now, and how it came to be wrong goes in the commit body.

## A deliberate change in how this plan is written

The previous sub-project's plan carried numbers its author had measured in a
scratch session. **Six of them were wrong**, and each was found by the
implementer running rather than transcribing. So this plan states numbers only
where they come from a file already in the repository, and everywhere else it
gives the **derivation command** and asks the implementer to pin what it
measures. A number you cannot re-derive is not a specification; it is a rumour.

Where this plan does give a figure, it says where it came from. Treat every one
as a claim to check, and correct the plan in your report if it is wrong.

## The three debts this plan discharges

`docs/superpowers/plans/carried-forward.md` hands this sub-project three
obligations. They are Tasks 1, 2 and 7 below, and none is optional:

1. **Reject `+nadgrids` and `proj4.defs`-alias definitions in
   `createTransformFromDefinition`** (Task 1). The seam is the builder, not the
   Worker init message, because the main thread builds a transform of its own at
   open time — measured, a `+nadgrids` definition puts a whole tileset of
   half-NaN bounding volumes in front of Cesium without a throw.
2. **Refuse `pointCount > 0` with `byteSize == 0`** (Task 2), where the file's
   claim is first read, so a defect in the file does not surface one layer down
   as an error blaming how the request was built.
3. **`resolveCrsDefinition` runs once, on the main thread** (Task 7). This
   module's entry point takes a definition and has no path that resolves one,
   and a boundary test proves the pipeline cannot reach the registry.

Task 1 also carries an instruction from `carried-forward.md`: **move the
measurement into the code with the guard.** The numbers behind it currently live
only in that file, so deleting the entry without carrying them loses the
evidence for why the check exists.

### Task 5: ECEF positions, an origin, and float32 relatives

**Files:**
- Create: `src/worker/positions.ts`
- Test: `tests/worker-positions.test.ts`

**Interfaces:**
- Consumes: `CrsTransform` from `src/crs/worker.js` (the barrel that reaches no registry), and the view from Task 4.
- Produces: `toRelativePositions(view: View, transform: CrsTransform): { rtcCenter: [number, number, number]; positions: Float32Array }`.

**The rule and its reason.** Decision 6 keeps positions as float32 relative to a
tile origin, because absolute ECEF is about 6.4 × 10⁶ m where float32 resolves
roughly half a metre. **RTC_CENTER is the midpoint of the transformed points'
ECEF bounding box** — the midpoint of what the tile actually contains, which is
what minimises the relatives that exist to be minimised.

- [ ] **Step 1: Write the failing tests**

Three properties, all of which hold whatever the numbers are:

1. **Round trip.** For every point, `rtcCenter + positions[i]` reproduces the
   ECEF the transform produced, to float32 resolution. Assert the *worst* error
   over all 47 points, not an average, and derive the tolerance from float32's
   precision at the magnitude of the relatives rather than picking a round
   number.
2. **The origin is inside the box.** `rtcCenter` lies within the min and max of
   the transformed points on each axis.
3. **The relatives are bounded by half the box.** No component of `positions`
   exceeds half the box's extent on its axis. This is what fails if the origin
   is computed from anything but the points.

- [ ] **Step 2: Run and watch fail**

- [ ] **Step 3: Implement**

One pass to transform and record the box, then a second over the same in-memory
array to write the relatives. Per-point `toEcef` allocation is accepted for v1
(the spec says so) — **measure it** in Step 5 rather than optimising it.

- [ ] **Step 4: Run and check**

- [ ] **Step 5: Mutations, and one measurement**

1. Use the node cube's centre as the origin instead of the points' box. Expected: property 3 loosens — report by how much on this chunk, since that number is the argument for the choice.
2. Write the absolute ECEF into the Float32Array. Expected: property 1 fails, and report the magnitude of the error — it should be the half-metre float32 resolution Decision 6 names.
3. Take the origin from the first point rather than the box midpoint. Expected: which property catches it?

**Measurement, recorded not asserted:** time `decodeChunk` and

### Task 6: The PNTS document

**Files:**
- Create: `src/worker/pnts.ts`
- Test: `tests/worker-pnts.test.ts`

**Interfaces:**
- Consumes: the view from Task 4 and `{ rtcCenter, positions }` from Task 5.
- Produces: `encodePnts(view: View, placed: { rtcCenter: [number, number, number]; positions: Float32Array }): ArrayBuffer`. The colour and the three batch-table attributes are read from the view here, with its getters, rather than being extracted by the caller — the view is the one place that knows which dimensions this point format carries, and splitting that knowledge across two modules is how the two would disagree.

**The layout is a contract on release — this is the last free moment to change
it.** A batch table's property names and types are what a caller's styles and
picking code are written against; once a version ships with `GpsTime` as a
double, removing it or narrowing it breaks their code rather than ours. The set
is therefore decided here, with the Cesium behaviour verified rather than
assumed. Copy this paragraph's substance into the module's doc comment.

**What ships, and why:** `POSITION` (float32 relatives) with `RTC_CENTER`; `RGB`
from the file's own colour, which Autzen carries because it is point format 7;
`BATCH_ID` per point, so a pick resolves to a point; and a batch table of
**classification, intensity and GPS time** — the three a point-cloud viewer
actually styles and filters on.

**GPS time is safe only because `BATCH_ID` is present, and the two cannot be
revisited separately.** Verified against the installed Cesium 1.143:
`Model/PntsLoader.js:557-559` forks on `const parseAsPropertyAttributes = !defined(parsedContent.batchIds);`
— with batch IDs the table becomes a property *table*, where
`parseBatchTable.js:439-440` transcodes `"DOUBLE"` to `"FLOAT64"` and precision
survives; without them it becomes property *attributes*, where the same file
casts to float32 and warns. Adjusted standard GPS time runs near 2.4 × 10⁸ s,
where float32 resolves about sixteen seconds. **Re-read those two files and
confirm both line numbers and both behaviours before you rely on them.**

- [ ] **Step 1: Write the failing test — Cesium reads back what we wrote**

This is the task's central check, and it is the same shape as the hierarchy
encoder's: our bytes are only evidence if the parser that will consume them
agrees. `@cesium/engine` is installed, so parse the emitted buffer with
`PntsParser.parse` from `node_modules/@cesium/engine/Source/Scene/PntsParser.js`
and assert what comes back: the point count, the RTC_CENTER, the positions, the
colours, and each batch-table property with its type.

Read that file first and let it tell you the header layout and the alignment it
requires, rather than encoding from memory and hoping. If `PntsParser` cannot be
imported in this environment, say so in your report and fall back to parsing the
header by hand — but try it first.

Then one property test that does not depend on the parser: reconstructing
`rtcCenter + position` for every point reproduces the ECEF the transform
produced, to float32 resolution. That is the assertion that catches a wrong
byte offset, a wrong alignment, or an origin that does not match its relatives.

- [ ] **Step 2: Run and watch fail**

- [ ] **Step 3: Implement**

Header, feature table JSON and binary, batch table JSON and binary. `BATCH_ID`'s
component type depends on the point count — decide the threshold from the 3D
Tiles rules and say what you chose.

- [ ] **Step 4: Run and check**

- [ ] **Step 5: Mutations**

1. Drop the padding that aligns the binary body. Expected: does `PntsParser` complain, or does it silently read shifted values? Report which — a parser that tolerates it means the round trip is weaker than it looks.
2. Write `POINTS_LENGTH` as one less than the true count.
3. Swap two batch-table properties' byte offsets.
4. Emit `BATCH_ID` as the wrong component type for the count.

Each must redden something. Any that does not is a coverage hole; report it.

- [ ] **Step 6: Commit**


### Task 7: The pipeline, and the realm boundary that proves the third debt

**Files:**
- Create: `src/worker/pipeline.ts`
- Test: `tests/worker-pipeline.test.ts`, `tests/worker-boundary.test.ts`

**Interfaces:**
- Produces: `encodeNode(input: { compressed: Uint8Array; header: DecodeHeader; pointCount: number; definition: string }): Promise<ArrayBuffer>`.

**The third debt.** `resolveCrsDefinition` runs once, on the main thread, at open
time, and its answer rides the Worker's init message — it throws
`CrsNotRegisteredError` and `CrsCodeNotFoundError`, which have to surface where
`fromUrl` can reject, and the same throw inside a Worker becomes an opaque
`messageerror`. This entry point therefore takes a **definition** and must have
no path that resolves one. That is not a convention to be trusted: pin it the
way `tests/crs-worker-boundary.test.ts` pins its own, by walking this module's
transitive import closure and asserting the registry is not in it.

**Zero points is a bug, not a case.** Decision 6 forbids serving a zero-point
PNTS by any path — such a tile never reaches ready and `tilesLoaded` waits
forever. The synthetic tileset omits content for a zero-point node and the COPC
specification gives it no bytes, so a chunk that decodes to zero points is a
defect in this library or in the file. Fail with a typed error.

1. The real chunk goes end to end and produces a buffer `PntsParser` reads back

2. A zero-point input raises the typed error rather than producing a buffer.

   contains `src/crs/transform.ts` and does **not** contain `src/crs/registry.ts`
   or `src/crs/resolve.ts`. Copy the closure walker from

- [ ] **Step 3: Implement**

Compose the three units. Nothing else belongs here.

- [ ] **Step 4: Run and check**

- [ ] **Step 5: Mutations**

## Done when

- One real 47-point chunk decodes, transforms, and encodes into a PNTS buffer that Cesium's own `PntsParser` reads back as 47 points.
- Reconstructing `RTC_CENTER + position` reproduces the transform's ECEF for every point, to float32 resolution.
- The decoded coordinates fall inside the header's declared bounds, which the decoder never saw.
